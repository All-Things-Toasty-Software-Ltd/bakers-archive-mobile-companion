# Android Release Signing

## Local development

If no `android/key.properties` exists, the release build type falls back to the debug keystore so `flutter run --release` and local APKs work on any machine. This is not acceptable for distribution and Toasty Deployer never relies on it.

## Toasty Deployer

The Linux builder:

1. Clones `main` into a temporary workspace.
2. Copies the production Android keystore into the temporary area (or points `storeFile` at it directly).
3. Writes `android/key.properties` only for the duration of the build.
4. Calls `flutter build apk --release` and `flutter build appbundle --release`.
5. Deletes `android/key.properties` via a trap even when a build step fails.

Expected properties:

```properties
storeFile=/opt/toasty-deployer/secrets/android-release.jks
storePassword=...
keyAlias=...
keyPassword=...
```

## Gradle integration

`android/app/build.gradle.kts` reads the properties file at sync time and creates a `release` `signingConfig`. The release `buildTypes` entry chooses it when the file exists and falls back to `debug` otherwise.

## Verifying the signature

After the build the Linux pipeline runs `apksigner verify --verbose` when the Android build-tools are available. A successful verification is required before any release is created.

## Distribution

- **GitHub releases** — APK only, intended for sideloading and source history.
- **GitLab releases** — APK attached to the self-hosted project's release, for internal testing and record keeping.
- **Google Play** — AAB uploaded through the Play Developer API helper.

No APK or AAB is committed to the repository; both are generated by the deployer.
